# RAG 功能创意筛选

## 当前产品基础

当前产品已经自然积累两类家庭历史：

- 事项：名称、类型、截止日期、备注、两人的留言、处理过程和完成结果。
- 账本：金额、日期、类目、付款人、备注和凭证图。

这些内容都由两个人在正常使用事项和账本时产生，不需要为了 AI 再维护一套资料。但现阶段单条文字较短，事项与账目也没有直接关联，因此不适合一开始就做无边界的“问我们家”聊天机器人。

本轮共生成 24 个候选方向，筛选标准是：必须真的需要从家庭历史中找资料、无需长期额外录入、答案能指出依据、出错不会造成严重后果，并且值得承担识别和生成成本。

## 推荐方向

### 1. “上次怎么处理的”相似事项回顾

**功能描述：** 用户新建或打开一个事项时，系统从已经完成的事项、备注和留言中找到相似经历，显示一张“上次处理记录”卡片。例如新增“空调漏水”，可以看到上次是谁处理、当时留下了什么说明、最终何时完成，并能点回原记录核对。

**推荐理由：** 这是现有数据最自然的延伸。内容会随着正常使用逐渐积累，不要求用户另建知识库；它解决的是“我们以前是不是处理过、当时怎么弄的”，而不是泛泛聊天。RAG 在这里有明确作用：找到文字不同但含义相近的历史记录，再把相关片段连同出处交给用户。

**不足：** 新家庭或使用时间短时几乎没有结果；记录过于简短时帮助有限；必须显示原记录入口，不能只给一段无法核对的总结。

**信心：** 86%

**复杂度：** 中等

**状态：** 讨论后暂缓，用户更希望优先增强高频使用的账本

### 2. 家庭经验卡

**功能描述：** 当某个事项的留言中出现可复用信息，例如维修电话、门锁处理办法、物业报修步骤，事项完成后提示“是否保存为家庭经验”。用户确认后形成一张简短经验卡；以后处理相似事项时自动找出相关卡片。

**推荐理由：** 相比直接检索所有历史，经过双方确认的经验更可靠，也会逐渐形成真正属于这个家的小型知识库。保存动作发生在事项完成时，只需一次确认，不是周期性手工导入。

**不足：** 多了一次确认操作；如果提示过于频繁会令人厌烦；经验可能过期，因此要显示来源和保存时间，并允许删除或标记失效。

**信心：** 76%

**复杂度：** 中等

**状态：** 待进一步讨论

### 3. 凭证与售后资料查找

**功能描述：** 在已有账目凭证图的基础上，识别购买时间、商家、商品和票据关键信息。用户可以问“扫地机器人是哪天买的”“把上次买热水器的凭证找出来”，结果直接定位到账目和原图，而不是只返回一句回答。

**推荐理由：** 用户已经可能在记账时上传凭证，不需要再次导入；票据文字和账目备注适合按含义查找；在退换、维修和报销时价值很具体。

**不足：** 使用频率低于第一名；图片识别会增加费用和隐私处理工作；没有上传凭证时无法使用；保修期等信息若票据未写明，不能猜测。

**信心：** 68%

**复杂度：** 高

**状态：** 待进一步讨论

### 4. 用一句话找账

**功能描述：** 用户用日常语言描述记不清具体条件的账目，例如“上个月我付的那顿火锅”或“去年买电饭煲的记录”，小程序结合金额、日期、付款人、类目、备注和凭证内容列出可能对应的原始账目。

**推荐理由：** 账本是当前更高频的模块，已有筛选适合条件明确的查找，但无法处理“只记得大概发生了什么”的情况。结果直接落到原始账目，用户可以核对，不依赖一段无法验证的回答。

**不足：** 很多查找仍可由普通筛选完成；备注和凭证不足时只能按明确字段查找；凭证文字识别会增加费用与隐私处理工作。

**信心：** 82%

**复杂度：** 中等

**状态：** 已完成需求讨论

## 淘汰方向

| 候选方向 | 淘汰原因 |
| --- | --- |
| 通用“问我们家”聊天机器人 | 范围太大，当前文字积累不足，容易出现看似会答但没有可靠依据的结果。 |
| “这个月为什么花多了” | 主要依赖结构化统计；备注覆盖率不足，生成解释容易把猜测当原因。 |
| 每周或每月家庭总结 | 属于汇总生成功能，检索不是核心，而且现有统计与首页概览已覆盖一部分价值。 |
| 自动预测快没了 | 需要稳定的购买数量和消耗周期，现有账目数据无法可靠推算。 |
| 自动生成重复事项 | 用规则或模板更便宜、更稳定，RAG 不是必要条件。 |
| 事项智能分类 | 三种事项类型很简单，直接选择比引入检索和生成更合适。 |
| 账目自动分类 | 更适合规则或单次分类模型，不属于 RAG。 |
| 两人矛盾调解 | 风险高，历史留言也不应被模型拿来判断谁对谁错。 |
| 家庭情绪分析 | 容易误解简短留言，价值不清晰且会造成被监视感。 |
| 家庭健康问答 | 属于高风险建议，现有产品也没有可靠的健康资料来源。 |
| 菜谱和采购建议 | 当前没有饮食偏好、库存和菜谱资料，无法从项目现有数据中成立。 |
| 礼物与纪念日记忆 | 当前数据来源零散，使用频率低，也与事项和账本主流程连接较弱。 |
| 家庭成员画像 | 两人场景没有必要，被总结和贴标签还可能带来反感。 |
| 消费决策复盘 | 账目只能证明买过，不能证明当时为什么买或使用感受如何。 |
| “有没有重复买”提醒 | 需要家庭库存和商品数量，单靠账目与凭证无法判断是否仍有存货。 |
| 维修商推荐 | 家庭历史样本太少，无法形成可信推荐；保留联系电话可并入家庭经验卡。 |
| 搬家资料助手 | 场景低频，且需要额外收集大量文档。 |
| 家庭规约问答 | 需要双方先专门编写规约，增加了一套持续维护负担。 |
| 家电说明书问答 | RAG 适配度高，但需要用户逐份上传说明书，和当前主流程关系较远。 |
| 全部留言语义搜索 | 是第一名的底层能力，不值得单独成为用户可见的新模块。 |

## 最终判断

如果只选一个方向，优先做“上次怎么处理的”，而且第一版应是一张有来源的相似记录卡，不应先做聊天页面。

建议先观察真实数据：至少有一批家庭连续使用一段时间，且完成事项中确实经常包含备注或留言，再决定是否投入。若大多数完成事项只有标题和完成时间，RAG 找不到有价值的上下文，此时不加功能反而是正确选择。

- 2026-08-30：“问账本”支持当前页面内连续追问，退出后清空且两位成员互不可见；第一版只读取金额、日期、付款人、收支类型、类目和文字备注，不读取凭证图片；没有足够依据时明确说明，不允许猜测或补充通用建议。
- 2026-08-30：完成“问账本”需求讨论，确定回答展示最多 5 条关键账目并可查看全部；需求落于 `docs/brainstorms/2026-08-30-ledger-rag-qa-requirements.md`。
