# 从需求讨论到实际交付的文档闭环

## Context

项目从 2026 年 8 月中旬开始，先后用 PRD 固定产品边界，用 brainstorm 收敛不确定需求，再用 plan 拆分实施单元。登录、家庭、事项、账本、自定义头像、问账本、共同足迹和全局快速新增均已形成实际功能与提交记录。

回看这些交付记录时，不能只按文件是否存在或复选框是否勾选判断完成状态：有些早期计划已经被后续提交完整吸收，但复选框仍为空；另一些功能已经通过自动检查，却仍缺微信开发者工具或手机上的最终确认。因此，项目需要一套统一的回溯和后续执行口径。

本次整理以当前仓库中的产品文档、功能代码、提交记录、README 和验证记录为主要证据。Codex 历史会话的专用检索脚本因当前电脑缺少 Bash 环境而无法启动，未读取会话原文件，也没有用其他资料冒充会话检索结果。

## Guidance

### 1. 用三层文档分别回答三个问题

- PRD 回答“为什么做、给谁用、必须满足什么、明确不做什么”。需求确认后，它是产品规则的唯一依据。
- brainstorm 回答“需求还不清楚时，哪些方向被比较过、为什么选择当前方向、还有哪些问题待确认”。一旦结论进入 PRD 或 plan，后续以新文档为准。
- plan 回答“如何按可验证的小单元实现”。每个单元都应对应具体需求、改动范围、异常分支和验收方式。

不要让 plan 偷改产品规则，也不要让实现细节反向覆盖已经确认的 PRD。若产品规则变化，应先修订或新增 PRD，再调整计划和代码。

### 2. 用证据链判断“已执行”，不用单一状态字段判断

一个文档可认定为已被执行吸收，至少要找到以下两类证据：

1. 实际功能、页面、服务或检查用例已经存在。
2. 提交记录、README 或专项验证记录能说明它对应的交付范围。

最终状态按证据强度分成三档：

- 已落地并完成自动检查：功能存在，相关测试和微信构建有成功记录。
- 已落地，待实际环境确认：功能和自动检查已完成，但微信开发者工具、云端配置或手机交互仍有明确待验项。
- 仅有文档：没有实际功能证据，不纳入“已执行”经验。

计划中的复选框只是辅助信息。它与实际提交冲突时，应修正文档状态，但不能据此否定已经存在的交付，也不能把未验收项说成完成。

### 4. 明确排除没有实际交付证据的文档

`docs/prd/009-family-summary-notification-prd.md` 只有文档提交 `1ff18ca`，未找到对应功能、实施计划或验证记录，并且没有进入当前 PRD 目录索引，因此不纳入本次“已执行”经验。

`docs/ideation/2026-08-30-rag-features-ideation.md` 属于创意筛选记录，不是本次要求整理的三类文档。其中“问账本”方向已通过 brainstorm、PRD 和 plan 落地，其余标记为暂缓或待讨论的方向不能算作已执行。

### 5. 从这些交付中保留的共同做法

#### 产品边界先于实现

每个模块先确定范围边界和成功标准，再决定页面、数据和云端处理。账本没有顺手加入 AA、预算和 OCR；足迹导航没有顺手增加后台到达检测；快速新增没有扩成全站导航改造。这种克制让每次交付都能独立验证。

#### 身份、家庭和数据权限由云端确认

登录、邀请、事项、账本、问账本和足迹都遵守同一原则：客户端只提出操作，家庭归属、权限、有效性和最终结果由云端确认。任何新功能只要涉及家庭数据，就应继续沿用这个边界。

#### 异常状态与正常流程同时设计

加载、失败、空状态、取消、重复点击、超时和重试不能等页面完成后再补。登录的启动恢复、事项的重复操作保护、问账本的额度与失败不扣次数、足迹的地图失败不阻断列表、快速新增的跳转锁，都是把异常分支提前写进需求后才稳定下来的。

#### 按可独立检查的小单元推进

可靠的顺序通常是：先固定数据和结果约定，再实现云端规则，然后接前端状态，最后制作页面和完成跨端验收。共同事项和账本的提交历史最清楚地体现了这种顺序。跨页面改动则先交付公共入口，再逐页接入，避免一次修改后无法定位问题。

#### 自动检查和实际环境确认分开记录

样式、类型、单元测试、微信构建和包体积可以自动确认；真实页面层级、地图跳转、登录授权、双账号协作和云端配置仍需要微信开发者工具或手机确认。自动化超时、跳过或只能打开登录页，都不能写成页面验收通过。

#### 状态文档要随交付收口

本次发现多个计划的实施单元仍显示未勾选，但 README 和提交已经证明功能落地。以后每次完成实施单元时，应同步更新计划、PRD 目录和 README；如果只完成代码而没完成手机确认，就明确写“已实现，待实际环境确认”，不要只写“已完成”。

## Why This Matters

这套口径解决了两个相反的问题：一是旧复选框没有更新，导致未来重复开发已经交付的功能；二是自动检查通过后过早宣布完成，掩盖手机交互、微信窗口和云端配置仍未确认的事实。

将产品规则、实施路径和验证证据分开保存，可以让后续工作直接继承已经确认的边界，同时清楚知道哪些结论仍需要实际环境复核。这样既不会因为历史文档过多而失去方向，也不会把计划本身当成成果。

## When to Apply

- 新需求从讨论进入 PRD、计划和开发时。
- 接手已有模块，需要判断某份文档是否已经执行时。
- 计划复选框、PRD 状态、README 和实际代码互相矛盾时。
- 自动检查已经通过，但微信开发者工具、手机或云端环境尚未确认时。
- 一个新想法可能扩大原有模块范围，需要判断应修改旧 PRD 还是新建 PRD 时。

## Examples

### 例一：正确判断旧计划是否已经执行

不能因为 `docs/plans/2026-08-30-002-feat-ledger-rag-qa-plan.md` 的六个实施单元仍未勾选，就认定“问账本”没有实现。应同时检查 `d941a48`、当前页面与云端功能、README 和相关检查用例。证据一致时，结论是“功能已落地，计划状态需要收口”。

### 例二：正确描述尚未完全验收的功能

足迹导航已经有实现、回归检查和微信构建成功记录，但手机地图跳转仍未确认。正确状态是“已实现，待真机验证”，而不是“未实现”，也不是“已经全部验收”。

### 例三：识别只有文档、没有交付的需求

家庭账目周报推送只有 PRD 文件和文档提交，没有实施计划、功能代码或验证记录。它只能算历史草案，不能进入已执行清单；如果未来重新启动，应先重新确认价值、平台限制和当前产品方向。

### 例四：新需求的最小闭环

1. brainstorm 只在需求存在关键不确定性时使用，并记录被放弃方向和选择理由。
2. PRD 固定目标、范围、异常状态和成功标准，用户确认后再继续。
3. plan 将每条需求映射到小型实施单元，并为每个单元写明检查方式。
4. 实现后运行自动检查，再完成微信开发者工具、手机和云端所需的实际确认。
5. 同步更新计划、PRD 目录和 README，真实记录“已完成”或“待实际环境确认”。
